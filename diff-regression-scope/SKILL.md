# 代码 Diff 回归范围分析器

## 技能定位

这个技能用于解决一个具体测试问题：

> 开发提交代码后，测试如何基于代码 Diff 反推影响面，并确定本次回归范围。

不要把任务做成单纯的“代码变更摘要”。代码摘要只是中间步骤，最终目标是输出能指导测试执行的回归范围。

## 适用输入

支持以下任意一种或多种输入：

- Git Diff / PR Diff / Merge Request Diff
- 变更文件清单、变更函数、提交说明
- 需求背景、Bug 修复说明、提测说明
- 模块关系、接口调用链、历史缺陷信息
- 现有测试用例或自动化覆盖情况

如果用户只给了变更描述，没有 Diff，也可以先基于描述分析，但必须把缺失信息列入“待确认项”。

## 必读规则

执行时先阅读：

- `rules/_sections.md`

再按任务需要阅读：

- `rules/diff-impact-analysis.md`：从 Diff 识别影响面的规则
- `rules/regression-priority.md`：回归范围和优先级判定规则
- `rules/artifact-file-output.md`：文件落地规则

## 工作原则

1. 始终围绕“这次要回归什么”展开，而不是停留在“代码改了什么”。
2. 先建立事实层：变更文件、变更逻辑、接口/状态/字段/异常处理变化。
3. 再推影响面：直接影响、间接影响、上下游调用、共享组件、数据兼容。
4. 再判风险：高/中/低风险必须给出原因，不允许只打标签。
5. 最后落地回归范围：必测、建议测、可抽测、可暂不测都要说明依据。
6. AI 输出是候选清单，必须保留“人工审查结论”和“待确认项”。

## 标准工作流

```text
Task Progress:
- [ ] Step 1: 解析 Diff，提取事实层变更
- [ ] Step 2: 识别直接影响模块和功能点
- [ ] Step 3: 识别间接影响、上下游链路和兼容风险
- [ ] Step 4: 评估风险等级并反推回归优先级
- [ ] Step 5: 输出必测 / 建议测 / 可抽测范围
- [ ] Step 6: 落地 Markdown 分析报告
```

## 输出要求

默认至少输出 1 个 Markdown 文件：

```text
outputs/analysis/<slug>.md
```

最终回复必须给出文件路径，并简要说明：

- 本次核心变更是什么
- 最高风险在哪里
- 必测回归范围是什么
- 哪些点需要人工确认

## 质量门槛

- 不能只输出“建议回归相关模块”，必须写清具体回归项。
- 每个必测项必须能追溯到 Diff 中的某个变更或明确影响链路。
- 每个高风险项必须说明触发条件和可能后果。
- 如果 Diff 信息不足，必须列出待确认问题，不能装作已经确定。
- 结果必须能被测试人员直接拿去做回归评审或测试执行安排。

## 快速触发示例

- “这是这次 PR 的 Git Diff，帮我分析影响面和回归范围。”
- “根据这段代码 Diff，判断这次必须回归哪些功能。”
- “帮我从这个 Bug 修复 Diff 反推回归测试清单。”
- “开发说只是小改动，帮我看下 Diff 里有没有隐藏风险。”
- “根据 main 和 feature 分支差异，输出回归范围和优先级。”
